# Agent Instructions

## Repository Shape

- This is the Go 1.26 module `github.com/donkeyx/dead-drop`.
- `blob/` owns the versioned SEAL v1 format and client-side encryption/decryption; the server treats blob bytes as opaque.
- `store/` owns filesystem, SQLite, and PostgreSQL persistence. HTTP download must use atomic `Store.Take`, never `Get` followed by conditional delete.
- `server/` is the stdlib `net/http` API; `cmd/dead-drop` contains offline and network CLI commands; `cmd/dead-drop-wasm` exposes the same `blob` package to browsers.
- `web/static/` contains checked-in JavaScript glue and vector harness inputs; generated `dead-drop.wasm` and `wasm_exec.js` are ignored and regenerated by `make wasm`.

## Development

- Run `go test ./...` for the normal suite; use `go test -race ./...` before security-sensitive changes.
- Run `go build -o bin/dead-drop ./cmd/dead-drop` or `make build` for the CLI.
- Run `make vectors` after changing the normative blob implementation or golden vectors; it regenerates vectors and then runs all tests.
- Run `make wasm-test` to rebuild the WASM module and run the Node golden-vector interop harness. It requires `make`, Node, and a Go toolchain with JS/WASM support.
- Run `gofmt` on changed Go files. There is no separate repository lint configuration.
- Passphrases must come from an environment variable or prompt, never command-line arguments; avoid logging plaintext, keys, fragments, passphrases, or raw blobs.

## Security And Deployment Constraints

- The master key belongs only in the URL fragment; never put it in a query, path, cookie, storage, log, or server response.
- Burn-after-read defaults on and must remain atomic: a concurrent burn `Take` has exactly one winner, and a failed response after `Take` still consumes the drop.
- FS/SQLite are single-writer/single-node against a local data directory. Use PostgreSQL with `DEADDROP_DATABASE_URL` for multiple replicas; PostgreSQL `Take` must retain row-lock/transaction atomicity across pods.
- PostgreSQL does not make the in-memory rate limiter global; shared rate limiting is still a separate deployment concern for HPA.
- Keep the no-CORS design and same-origin browser crypto boundary. The server must never receive plaintext or decrypt keys.
- `DEADDROP_TRUST_PROXY=true` requires a non-empty trusted CIDR list; fail closed rather than trusting arbitrary forwarded headers.

## Current Scope

- PR1-PR6 are complete: SEAL library, offline CLI, FS/SQLite stores, HTTP API, network put/get, and WASM crypto/vector harness.
- PR7 is the browser UI slice: server-rendered create/reveal shells plus same-origin static JS around the existing client-side WASM crypto. If HTMX is added later for non-sensitive chrome, it must never submit plaintext, fragment keys, or passphrases.
- The design and README are the source of product/security constraints; preserve their wording around “client-side encrypted” and avoid unqualified “zero-knowledge” claims.
